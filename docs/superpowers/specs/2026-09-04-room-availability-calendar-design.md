# 空房日曆設計

**日期**：2026-09-04
**狀態**：待審
**目標**：在 `/stay` 顯示未來的空房狀況，讓客人在詢問前就知道哪些日子還訂得到。

---

## 1. 背景與限制

管理端現況：兩間房，一間房一本 Google 日曆（**荷花**、**遠山**），訂房直接建在日曆上。
Google 試算表另有記錄，但日曆才是「這天有沒有被訂走」的權威來源。

硬限制：

- **不能花錢。**
- 網站是純前端 SPA，部署在 Vercel。沒有後端、沒有資料庫，README 明列這是刻意的設計。
- repo 是**公開**的 —— 任何 commit 進去的檔案全世界都看得到。
- 客人姓名絕對不能外流。

## 2. 前置驗證（已完成）

動工前先實測兩本日曆的公開 `.ics`，六項全部通過：

| 驗證項目 | 結果 |
| --- | --- |
| 公開 `.ics` 抓不抓得到 | ✅ 兩本都回 `HTTP 200`（2798 / 2216 bytes） |
| 隱私設定是否已擋掉詳細資訊 | ✅ 16 筆訂房的 `SUMMARY` **只有一個相異值**：字面上的 `Busy` |
| `ATTENDEE` 是否含客人信箱 | ✅ 否，是日曆自己的 ID |
| 日期型態 | ✅ 全部是全天事件（`VALUE=DATE`），不受時區影響 |
| 房間名稱來源 | ✅ feed 內含 `X-WR-CALNAME`（`訂房-荷花` / `訂房-遠山`） |
| feed 是否包含未來事件 | ✅ 遠山有 `20261022`，今天是 `20260904` |

第二項是整個方案的前提。16 筆不同的訂房卻只有一種標題，證明 Google 確實把詳細資訊擋住了 ——
如果日曆被誤設成「查看所有活動詳細資訊」，這裡會出現 16 個不同的值（通常是客人姓名）。

> ⚠️ 這個設定是**在 Google 那一端**，不在程式裡。日後若有人改動日曆的共用設定，
> 姓名就會透過那個公開網址外流，而且網站這邊不會有任何徵兆。
> 因應方式見 §6。

## 3. 架構決策

### 採用：排程產生 JSON，跟著網站一起出貨

沿用 repo 既有且已驗證的模式 —— `update-events.yml` 每天抓 TDX、寫
`events.generated.json`、有變動才 commit、Vercel 自動重部署。空房日曆完全複製這套流程。

### 為什麼不用其他做法

| 方案 | 為什麼不用 |
| --- | --- |
| 嵌入 Google 日曆 iframe | 顯示的是「已訂」而非「可訂」，跟需求相反；Google 的 UI 與全站視覺落差大、手機上尤其糟；且需要日曆全公開 |
| 前端即時 fetch `.ics` | 多一個 runtime 依賴：Google 慢或不通，日曆就開天窗。且 `.ics` 沒有 CORS 標頭，瀏覽器直接擋 |
| Google Apps Script 當 API | 隱私最好（日曆可完全不公開），但多一個屋主要自行維護、壞了不好修的元件。既然 §2 證實 free/busy 的公開 feed 就夠用，不需要這一層 |

排程方案的額外好處：**沒有 runtime 依賴**。資料跟著網站一起出貨，
就算 Google 掛掉、或客人的網路擋 Google，日曆照樣顯示。

### 要接受的代價

資料是建置時固定的，客人看到的是上次排程跑完的狀態。

- 排程設**每小時**。公開 repo 的 Actions 分鐘數無上限，成本為零。
- 最壞情況：剛被訂走的日期，網站還顯示可訂約一小時。
- 因為訂房流程是「填表單 → LINE 確認」而非線上即時成交，這個延遲可接受。
- 但頁面上**必須**顯示資料更新時間，並註明「實際空房以詢問為準」。

> GitHub 的排程工作在尖峰時可能延遲，「每小時」是盡力而為不是保證。
> 另外 GitHub 會停用「60 天無活動」repo 的排程 —— 本 repo 因為活動資料每天都在 commit，不受影響。

## 4. 資料流

```
Google 日曆（荷花 / 遠山，設定為「只顯示空/忙」）
        │  公開 .ics
        ▼
GitHub Actions（每小時）
  scripts/fetch-availability.mjs
        │  只取日期，其餘欄位一律丟棄
        ▼
src/data/availability.generated.json   ← 有變動才 commit
        ▼
Vercel 自動重新部署
        ▼
AvailabilityCalendar.jsx
```

## 5. 產出的資料格式

```json
{
  "generatedAt": "2026-09-04T18:05:00+08:00",
  "rooms": [
    { "id": "lotus", "name": "荷花" },
    { "id": "mountain", "name": "遠山" }
  ],
  "booked": {
    "2026-10-22": ["mountain"]
  }
}
```

設計說明：

- **只記「被訂走的日期」，不記可訂的日期。** 沒出現在 `booked` 裡的日期就是全空。
  避免產生一份無限長、還要決定「未來要列到哪一天」的清單。
- **記錄是哪一間被訂，而不只是數量。** 資訊嚴格較多，UI 要顯示數量或房名都行。
  這不構成額外的隱私暴露 —— 兩本 `.ics` 本來就是公開的，任何人都推得出同樣資訊。
- **只保留今天（含）以後的日期。** feed 會回傳數個月前的舊訂房（實測回到 7 月），
  對「還訂得到嗎」毫無用處，留著只會讓檔案愈長愈大。以 Asia/Taipei 的今天為界過濾。
- **檔案裡不會有任何客人資訊。** 腳本只讀 `DTSTART` / `DTEND`，
  連 `SUMMARY` 都不讀取（即使它目前只是 `Busy`）。這是對 §2 那個警告的程式層防呆：
  就算哪天 Google 的共用設定被改錯，也不會有姓名寫進這個公開 repo。

## 6. 關鍵邏輯：`DTEND` 是「不包含」的

**這是整個功能風險最高的一行邏輯。**

實測資料中，荷花有兩筆連著的訂房：

```
DTSTART:20260719  DTEND:20260721   ← 訂房 A
DTSTART:20260721  DTEND:20260724   ← 訂房 B
```

7/21 同時是 A 的 `DTEND` 與 B 的 `DTSTART`。這不是重複訂房，而是 A 當天早上退房、
B 當天下午入住。也就是 iCal 全天事件的 `DTEND` **不包含**當天。

> **規則：佔用的夜晚 = `DTSTART` 到 `DTEND` 的前一天。**

寫錯的後果分兩種，都很實際：

- 把 `DTEND` 算進去 → 退房日被誤標客滿，**白白少接一天生意**
- 少算一天 → 已住宿的夜晚顯示可訂，**造成重複訂房**

因應：腳本提供 `--check` 模式，印出每間房每一筆的「入住日 → 佔用夜晚清單」供人工核對。
專案沒有測試框架，本次不引入；這個邊界改為以實際資料肉眼驗證。

## 7. 失敗處理

**任何一本日曆抓失敗，就整個中止、不寫檔、workflow 標記失敗。**

理由：若荷花抓失敗而只寫入遠山的資料，荷花會被當成全月皆空 ——
**抓取失敗會直接偽裝成「有空房」**，這是最糟的失敗模式。寧可讓資料停留在舊狀態。

前端對應：`generatedAt` 超過 24 小時，更新時間改以警示色顯示，
讓屋主自己看得出排程壞了。（客人看到的仍是舊資料，但至少標示了時間。）

## 8. 前端設計

### 呈現方式

月曆格線，一次顯示當月，可往前往後切換月份。每一格：

- 日期數字
- **每間房一個點**，實心＝可訂、空心＝已訂。兩間房就是兩個點

用點而不是文字的原因：手機 375px 寬、七欄格線，每格只有約 45px，
塞不下「剩 1 間」這種字。點是語言無關的，且日後增加房間也能直接擴充。

搭配圖例說明。過去的日期整格灰掉、不可互動。

**「今天」一律以 Asia/Taipei 判定，不用瀏覽器所在時區。** 民宿在台東，
入住日就是台灣時間；若跟著瀏覽器時區跑，人在美國的客人會看到差一天的月曆。

**可切換的月份範圍：當月起算往後 6 個月，不能往前切到過去的月份。**
往回看已經過去的日期對訂房沒有意義，還會讓人以為訂得到。

### 必要的文字

- `更新於 2026-09-04 18:05`
- `實際空房以詢問為準，確認後才算訂房成功`

第二句不是免責聲明的形式主義 —— 它處理的是 §3 那一小時的資料延遲。

### 無障礙

點是視覺呈現，每一格另外提供 `aria-label`，
例如「10 月 22 日，剩 1 間可訂」。不能只靠顏色與形狀傳達狀態。

## 9. 頁面位置

放在 `/stay`，**獨立成一個新 section，接在「環境介紹」之後**。

同時要調整既有程式：**把「環境介紹」尾端那顆「立即訂房」按鈕移到空房日曆的下方。**

理由是動線。現在的順序是「看完環境 → 訂房」，加入日曆後應該變成：

```
看環境 → 看照片 → 問房間 → 看設施 → 查有沒有空 → 訂房
```

若把日曆插在訂房按鈕之後，等於「叫人下訂 → 才給看有沒有空」，順序是反的；
若兩個區塊各留一顆訂房按鈕，兩顆會靠得太近，反而稀釋掉主要動作。

## 12. 已知風險

| 風險 | 影響 | 因應 |
| --- | --- | --- |
| 日曆共用設定被改成「查看所有活動詳細資訊」 | 客人姓名經由公開網址外流 | 腳本完全不讀 `SUMMARY`，公開 repo 裡不會有姓名。但**外流發生在 Google 那一端，程式擋不住**，屋主需知道不要改那個設定 |
| 排程延遲或失敗 | 顯示過期資料 | 顯示更新時間；超過 24 小時改警示色 |
| 一小時的資料延遲 | 剛訂走的日期仍顯示可訂 | 頁面註明以詢問為準 |
| `DTEND` 邊界寫錯 | 少接生意或重複訂房 | 見 §6，`--check` 模式人工核對 |
| 每小時 commit 造成 git 歷史變雜 | 倉庫肥大 | 沿用活動那套「有變動才 commit」；實際訂房異動一天僅數次 |
